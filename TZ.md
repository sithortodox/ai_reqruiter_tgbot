# Техническое задание для ИИ-агента-разработчика
## Разработка Telegram-бота для первичного AI-собеседования кандидатов

**Версия документа:** 1.0  
**Тип проекта:** Telegram-бот с интеграцией языковой модели (LLM)  
**Назначение:** Автоматизация первичного отбора соискателей и передачи результатов рекрутерам.

---

# 1. Роль ИИ-агента

Ты — ИИ-агент, выступающий в роли системного аналитика, архитектора ПО, backend-разработчика, инженера по интеграции LLM и специалиста по тестированию.

Твоя задача — самостоятельно спроектировать и реализовать работоспособный Telegram-бот для первичного собеседования кандидатов, соответствующий требованиям этого технического задания.

Ты должен пройти весь цикл разработки:

1. Проанализировать требования.
2. Определить архитектуру и технологический стек.
3. Спроектировать структуру данных и сценарии взаимодействия.
4. Реализовать Telegram-бота.
5. Подключить API языковой модели.
6. Реализовать оценку кандидатов и маршрутизацию результатов.
7. Настроить уведомления рекрутерам.
8. Добавить логирование, обработку ошибок и защиту от повторных запросов.
9. Провести автоматизированное и ручное тестирование.
10. Подготовить документацию по установке, настройке и эксплуатации.
11. Передать готовый проект и инструкции по запуску.

Не ограничивайся написанием примеров кода, псевдокода или архитектурных рекомендаций. Результатом должна стать полноценная система, которую можно развернуть на сервере и использовать в работе.

Если часть требований неоднозначна, сначала зафиксируй допущения. Не придумывай данные заказчика, параметры вакансии, API-ключи и идентификаторы Telegram-чатов. Все неизвестные параметры вынеси в конфигурацию.

# 2. Цель проекта

Разработать Telegram-бота, который автоматизирует первичный этап собеседования кандидатов.

Бот должен:

- Принимать обращения соискателей через Telegram.
- Собирать контактные данные и резюме.
- Последовательно задавать вопросы для первичного отбора.
- Сохранять ответы кандидата.
- Передавать собранные сведения языковой модели для анализа.
- Оценивать соответствие кандидата требованиям вакансии.
- Формировать структурированный отчет.
- Определять дальнейший маршрут кандидата на основании настраиваемых критериев.
- Отправлять подходящих кандидатов рекрутерам с высоким приоритетом.
- Сохранять неподходящих кандидатов в архиве и отправлять им вежливое сообщение.
- Предоставлять администратору возможность контролировать работу системы и изменять сценарии без переписывания основной логики.

# 3. Общая архитектура

Реализуй систему в виде модульного приложения с разделением ответственности.

Основные компоненты:

1. Telegram Bot API — взаимодействие с кандидатами и рекрутерами.
2. Диалоговый модуль — управление состояниями интервью.
3. Модуль обработки файлов — прием и извлечение текста из резюме.
4. Модуль AI-аналитики — оценка ответов кандидата с помощью LLM.
5. Модуль маршрутизации — определение следующего действия.
6. База данных — хранение кандидатов, ответов, оценок и статусов.
7. Модуль уведомлений — отправка отчетов в закрытый чат рекрутеров.
8. Административный модуль — настройка вакансий, вопросов и критериев оценки.
9. Модуль мониторинга — регистрация событий, ошибок и расхода токенов.

Предпочтительно использовать Python и асинхронный фреймворк для Telegram-ботов, PostgreSQL для постоянного хранения данных и Docker Compose для развертывания.

Для локальной разработки допускается SQLite, если это не мешает переходу на PostgreSQL.

Для интеграции с языковой моделью создай отдельный адаптер. Конкретного провайдера и модель выбирай после проверки требований к API, стоимости, доступности и качеству обработки русского языка.

Система должна быть модульной: замена LLM-провайдера не должна требовать переписывания диалоговой логики.

No-code/low-code подход допустим, если он обеспечивает устойчивую работу, управляемые сценарии и возможность изменять вопросы и промпты без изменения исходного кода. Если визуальная платформа не обеспечивает необходимые требования, реализуй конфигурируемый сценарий в приложении.

# 4. Функциональные требования

## 4.1. Запуск и регистрация кандидата

При переходе по ссылке на бота или выполнении команды `/start` кандидат должен получать приветственное сообщение с кратким описанием процесса.

Бот должен поддерживать:

- Запуск интервью.
- Повторный запуск после завершения предыдущей сессии.
- Проверку существующей незавершенной сессии.
- Возобновление интервью после перезапуска приложения.
- Защиту от случайного создания нескольких одинаковых сессий.
- Возможность корректно завершить или отменить интервью.

Каждая сессия должна иметь уникальный идентификатор.

Предусмотри возможность использования ссылки с параметром вакансии, например `?start=vacancy_123`, чтобы кандидат сразу попадал на интервью по нужной вакансии.

Если параметр отсутствует или вакансия не найдена, используй вакансию по умолчанию либо попроси администратора настроить доступный сценарий.

## 4.2. Сбор данных кандидата

На первом этапе бот должен собрать:

- ФИО или имя кандидата.
- Контактные данные.
- Telegram ID.
- Username, если он доступен.
- Резюме.
- Информацию о вакансии, на которую претендует кандидат.
- Дату и время начала интервью.

Контактные данные должны приниматься в виде текста или Telegram-контакта.

Резюме должно приниматься:

- В виде текстового сообщения.
- В виде документа, например PDF, DOCX или TXT.

Для каждого типа файла необходимо определить допустимый размер, проверить формат и безопасно обработать содержимое.

Если файл невозможно прочитать, бот должен сообщить об этом и предложить загрузить документ повторно либо вставить текст резюме в чат.

Если обязательные данные не получены, интервью не должно переходить к следующему этапу без соответствующего решения сценария.

Предусмотри уведомление о целях обработки персональных данных и получение необходимого подтверждения от кандидата до сбора и обработки данных. Текст уведомления должен настраиваться заказчиком.

## 4.3. Диалоговый модуль

После регистрации кандидат проходит последовательный сценарий собеседования.

Бот должен:

1. Получить активную конфигурацию вакансии.
2. Загрузить список вопросов.
3. Задать первый вопрос.
4. Сохранить ответ.
5. Проверить корректность и допустимую длину ответа.
6. Перейти к следующему вопросу.
7. Повторять процесс до завершения сценария.
8. Передать результаты в модуль AI-аналитики.
9. Дождаться результата анализа.
10. Выполнить маршрутизацию.
11. Отправить кандидату финальное сообщение.

Вопросы должны храниться в конфигурации, а не быть жестко зашиты в программный код.

Для каждого вопроса необходимо предусмотреть:

- Уникальный ID.
- Текст.
- Порядковый номер.
- Тип ответа.
- Признак обязательности.
- Ограничение длины ответа.
- Возможность включения и отключения вопроса.

В первой версии поддерживаются текстовые ответы. Возможность приема голосовых сообщений может быть добавлена отдельным расширением.

Команды управления диалогом:

- `/start` — запуск или возобновление сценария.
- `/cancel` — отмена текущего интервью.
- `/help` — инструкция по работе с ботом.

Если кандидат не отвечает в течение настраиваемого периода, сессия должна получить статус ожидания или истечения времени. При необходимости бот может отправить напоминание.

После завершения или отмены интервью новые ответы не должны изменять результаты завершенной сессии.

## 4.4. Обработка резюме

Реализуй отдельный модуль извлечения текста из загруженных документов.

Требования:

- Проверка расширения, MIME-типа и размера.
- Обработка ошибок чтения.
- Извлечение текстового содержимого PDF и DOCX.
- Сохранение исходного текста резюме.
- Связь резюме с кандидатом и конкретной сессией.
- Ограничение объема текста, передаваемого в LLM.
- Защита от вредоносных файлов и обработки неподдерживаемых форматов.

Если PDF содержит только сканированные изображения, система должна сообщить, что текст не удалось извлечь, либо использовать дополнительный OCR-модуль, если он предусмотрен конфигурацией.

Не передавай в языковую модель лишние персональные данные, не требующиеся для оценки квалификации.

## 4.5. Модуль AI-аналитики

Подключи языковую модель через API.

Модуль получает:

- Профиль вакансии.
- Обязательные требования.
- Желательные навыки.
- Список вопросов и ответов.
- Текст резюме.
- Критерии оценки.
- Инструкции для модели.

На основании этих данных модель формирует отчет о соответствии кандидата требованиям вакансии.

Отчет должен содержать:

1. Общую оценку от 1 до 10.
2. Краткое резюме кандидата.
3. Подтвержденные профессиональные навыки.
4. Релевантный опыт работы.
5. Сильные стороны.
6. Выявленные пробелы.
7. Несоответствия обязательным требованиям.
8. Стоп-факторы, если они установлены критериями вакансии.
9. Обоснование итоговой оценки.
10. Рекомендацию по следующему этапу.
11. Уровень уверенности анализа или отметку о недостаточности данных.
12. Перечень фактов, которые требуют дополнительной проверки.

Оценка должна опираться на конкретные сведения из резюме и ответов, а не на предположения модели.

Если информации недостаточно, модель должна явно сообщать об этом. Недостающие сведения нельзя считать подтвержденными навыками или опытом.

Не допускай оценки кандидатов на основании защищенных характеристик, не относящихся к профессиональным требованиям. Оценка должна учитывать квалификацию и критерии конкретной вакансии.

### Формат результата

Для внутреннего обмена данными используй структурированный JSON.

Пример схемы:

{
  "candidate_id": "candidate_123",
  "vacancy_id": "vacancy_123",
  "score": 8,
  "summary": "Краткое резюме кандидата",
  "skills": [
    {
      "name": "Python",
      "evidence": "Подтверждено ответом на вопрос 3",
      "level": "intermediate"
    }
  ],
  "strengths": [
    "Релевантный опыт"
  ],
  "gaps": [
    "Недостаточно подтвержден опыт работы с PostgreSQL"
  ],
  "stop_factors": [],
  "mandatory_requirements_met": true,
  "insufficient_data": false,
  "recommendation": "next_stage",
  "reasoning_summary": "Обоснование оценки на основе фактов",
  "confidence": "medium"
}

Это пример структуры, которую можно расширять. Все поля, их типы и допустимые значения должны быть формализованы в схеме валидации.

Результат от LLM необходимо проверять перед сохранением. Если JSON некорректен, отсутствуют обязательные поля или оценка выходит за диапазон 1–10, система должна выполнить ограниченное число повторных попыток либо перейти в состояние ошибки анализа.

Не допускай автоматического отказа из-за технической ошибки модели.

## 4.6. Системный промпт

Создай отдельный настраиваемый системный промпт для AI-аналитики.

Промпт должен определять:

- Роль модели — аналитик первичного отбора кандидатов.
- Цель анализа — оценка профессионального соответствия вакансии.
- Критерии оценки и их веса.
- Правила подтверждения навыков на основании фактов.
- Правила определения стоп-факторов.
- Формат структурированного ответа.
- Правила обработки недостаточной информации.
- Запрет на выдумывание фактов.
- Запрет на использование нерелевантных персональных характеристик.
- Правила рекомендации следующего этапа.

Предусмотри возможность разных промптов для разных вакансий.

Промпт должен версионироваться. Изменение промпта не должно менять уже сохраненные результаты ранее завершенных интервью.

## 4.7. Система оценки и маршрутизации

Реализуй маршрутизацию кандидатов на основе конфигурируемых критериев.

### Ветка A — кандидат соответствует требованиям

Если оценка достигает установленного порога и обязательные требования выполнены:

- Присвоить статус `recommended`.
- Отправить уведомление рекрутерам с высоким приоритетом.
- Передать карточку кандидата и полный отчет.
- Отправить кандидату сообщение о завершении первичного этапа и дальнейших действиях.

### Ветка B — кандидат не соответствует требованиям

Если критерии отбора не выполнены:

- Присвоить статус `not_recommended`.
- Сохранить анкету и отчет в архиве.
- Не отправлять срочное уведомление рекрутерам.
- Отправить кандидату вежливое сообщение о завершении этапа.

### Дополнительная ветка — требуется проверка

Если анализ завершился ошибкой, данных недостаточно или результат неоднозначен:

- Присвоить статус `manual_review`.
- Сохранить все полученные данные.
- Уведомить ответственного администратора или рекрутера.
- Не отправлять автоматический отказ до разрешения ситуации.

Порог оценки, веса критериев и обязательные требования должны задаваться в конфигурации вакансии.

Не считай одну итоговую оценку достаточным условием отказа, если не выполнены обязательные требования к прозрачности и проверке результата. Все критерии маршрутизации должны быть доступны администратору.

Автоматические рекомендации являются вспомогательным инструментом. Решение о найме или окончательном отказе должно оставаться под контролем ответственного сотрудника.

## 4.8. Карточка кандидата для рекрутера

После завершения анализа бот отправляет в закрытый Telegram-чат карточку кандидата.

Карточка должна содержать:

- ФИО.
- Контактные данные, необходимые для связи.
- Вакансию.
- Дату интервью.
- Итоговую оценку.
- Статус.
- Краткое резюме.
- Подтвержденные навыки.
- Сильные стороны.
- Выявленные пробелы.
- Стоп-факторы.
- Ответы на вопросы.
- Рекомендацию AI.
- Идентификатор сессии.

Предусмотри возможность прикрепления исходного резюме или ссылки на его защищенное хранение, если это требуется заказчику.

Не выводи лишние персональные данные в уведомление.

Для подходящих кандидатов сообщение должно визуально выделять высокий приоритет. Для кандидатов, которым требуется ручная проверка, указывай соответствующий статус.

Длинные отчеты необходимо разбивать на несколько сообщений или отправлять отдельным документом. Учитывай ограничения Telegram Bot API.

## 4.9. Администрирование

Предусмотри механизм управления настройками без изменения программного кода.

Минимально необходимые настройки:

- Список вакансий.
- Название и описание вакансии.
- Обязательные требования.
- Желательные навыки.
- Вопросы интервью.
- Порог оценки.
- Веса критериев.
- Стоп-факторы.
- Системный промпт.
- Тексты сообщений кандидату.
- ID чата рекрутеров.
- Тайм-аут интервью.
- Ограничения размера сообщений и файлов.
- Параметры интеграции с LLM.

В первой версии допускается реализация управления через защищенную административную команду, конфигурационный файл или простую веб-панель.

Административные функции должны быть недоступны обычным пользователям.

Изменения конфигурации должны сохраняться в базе данных или в контролируемом хранилище настроек.

При обновлении сценария уже начатые интервью должны продолжаться по той версии вопросов и промпта, с которой они были начаты.

## 4.10. Мониторинг и журналирование

Реализуй регистрацию ключевых событий:

- Запуск интервью.
- Сбор контактных данных.
- Получение резюме.
- Ответ на вопрос.
- Переход между шагами.
- Завершение и отмена сессии.
- Вызов LLM.
- Успешный и неуспешный анализ.
- Ошибка отправки сообщения.
- Изменение статуса кандидата.
- Отправка карточки рекрутеру.

Для вызовов LLM фиксируй:

- Провайдера и модель.
- Версию промпта.
- Время выполнения.
- Количество входных и выходных токенов, если эти данные доступны.
- Стоимость вызова, если ее можно достоверно определить.
- Статус выполнения.
- Код ошибки при сбое.

Не записывай API-ключи, пароли и другие секреты в логи.

Предусмотри обработку сетевых ошибок, повторные попытки с ограничением количества, задержки между повторами и уведомления администратора при критических сбоях.

# 5. Модель данных

Спроектируй базу данных как минимум со следующими сущностями.

### Candidates — кандидаты

# 6. Управление состояниями

Для интервью используй явную модель состояний.

Дополнительные состояния:

- `cancelled`
- `expired`
- `analysis_failed`
- `manual_review`

Переходы между состояниями должны быть валидируемыми.

Запрещается:

- Начинать анализ до завершения обязательных шагов.
- Отправлять финальную карточку повторно при повторной обработке одного события.
- Менять завершенную сессию из-за позднего сообщения.
- Терять текущее состояние после перезапуска приложения.
- Отправлять кандидату отказ при технической ошибке AI.

Реализуй идемпотентную обработку событий Telegram и защиту от дублирующихся уведомлений.

# 8. Технические требования

Рекомендуемый стек:

- **Язык:** Python.
- **Telegram:** aiogram или эквивалентный асинхронный фреймворк.
- **База данных:** PostgreSQL.
- **ORM и миграции:** SQLAlchemy и Alembic либо аналоги.
- **LLM:** API выбранного провайдера через отдельный адаптер.
- **Обработка документов:** библиотеки для PDF и DOCX.
- **Развертывание:** Docker и Docker Compose.
- **Тестирование:** pytest.
- **Логирование:** стандартный модуль logging или структурированный аналог.

Конкретные версии зависимостей должны быть зафиксированы в файле зависимостей.

Система должна поддерживать запуск в Linux-окружении и не требовать ручного вмешательства при штатном перезапуске контейнеров.

Для Telegram используй webhook или long polling. Выбор должен быть обоснован условиями эксплуатации.

Для первой версии не внедряй дополнительные очереди, микросервисы и сложную инфраструктуру без необходимости. При этом обработка длительного AI-анализа не должна блокировать прием других сообщений.

# 11. Обработка ошибок

Реализуй обработку следующих ситуаций:

- Telegram API временно недоступен.
- Пользователь отправил неподдерживаемый файл.
- Резюме не удалось прочитать.
- LLM API недоступен.
- Превышено время ожидания LLM.
- Превышены лимиты провайдера.
- Ответ LLM не соответствует схеме.
- База данных недоступна.
- Не удалось отправить карточку рекрутеру.
- Кандидат завершил диалог досрочно.
- Сессия истекла.
- Администратор изменил конфигурацию во время интервью.

Ошибки должны обрабатываться без потери уже сохраненных ответов.

Для повторяемых операций используй контролируемые повторы и защиту от дублирования. Для операций, требующих последующей доставки, предусмотри возможность повторной отправки после восстановления сервиса.

Пользователю показывай понятное сообщение. Подробности исключений и технические данные записывай в журнал.

# 13. План тестирования

Обязательно реализуй автоматические тесты и проведи проверку следующих сценариев.

### Функциональные тесты

1. Кандидат проходит интервью от начала до конца.
2. Кандидат отправляет резюме в PDF.
3. Кандидат отправляет резюме в DOCX.
4. Кандидат вставляет резюме текстом.
5. Кандидат отправляет поврежденный файл.
6. Кандидат отменяет интервью.
7. Сессия восстанавливается после перезапуска.
8. Повторное событие Telegram не дублирует ответ или отчет.
9. Подходящий кандидат получает статус `recommended`.
10. Неподходящий кандидат получает статус `not_recommended`.
11. Ошибка анализа переводит сессию в контролируемое состояние.
12. Неоднозначный результат направляется на ручную проверку.
13. Пользователь без административных прав не может менять настройки.
14. Изменение промпта не изменяет результаты старых интервью.

### Тесты AI-аналитики

Подготовь набор синтетических тестовых кандидатов:

- Полностью соответствующий требованиям.
- Частично соответствующий.
- Не соответствующий обязательным требованиям.
- С недостаточным опытом.
- С противоречивыми ответами.
- С неполным резюме.
- С ответами, содержащими попытки изменить инструкции модели.
- С нерелевантными личными сведениями.

Проверяй корректность JSON, обоснованность оценок и соответствие результата критериям вакансии.

Не считай субъективное впечатление модели доказательством точности. Результаты тестирования необходимо фиксировать и сравнивать с заранее определенными ожидаемыми результатами.

# Итоговая задача

Разработай полноценного Telegram-бота для первичного AI-собеседования кандидатов в соответствии с этим техническим заданием.

Приоритеты разработки:

1. Надежное сохранение данных и состояния интервью.
2. Корректная последовательность диалога.
3. Предсказуемая интеграция с LLM.
4. Проверяемая оценка и прозрачная маршрутизация.
5. Безопасная обработка персональных данных.
6. Удобное администрирование.
7. Простое развертывание и сопровождение.

**Главный критерий успеха:** заказчик должен получить работающий инструмент, в котором кандидат проходит интервью в Telegram, нейросеть анализирует его ответы, а рекрутер получает структурированный отчет без необходимости вручную собирать информацию из переписки.
